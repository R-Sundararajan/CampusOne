# Input validation hardening

This document records the input validation improvements made across CampusOne. The backend remains authoritative: browser checks improve feedback, while routes and services validate every request that can change or read application data.

## Before and after

| Area | Before | After | Workflow improvement |
| --- | --- | --- | --- |
| Human-entered text | Schemas repeated trimming and length rules, but did not consistently normalize Unicode or reject control characters. | A shared `textField` validator normalizes to NFC, trims outer whitespace, applies each field's length bounds, and rejects control characters. Multiline fields keep tabs and line breaks. It is used across Registration, Attendance, Events, Complaints, and Club Access. | Equivalent text has a consistent stored form, blank-looking values are rejected where text is required, and control characters are less likely to create confusing names, labels, notes, or audit entries. |
| Cross-field and conditional rules | Some invalid combinations were rejected only later in services, and some forms allowed users to submit combinations the server would reject. | Schemas and forms now check identity-confirmation conflicts, synthetic-attestation evidence, revocation payloads, and other conditional requirements. Database-dependent checks remain in services. Event edits preserve omitted date fields, then validate the combined schedule. | Users get earlier, clearer feedback, and updates are less likely to clear a schedule accidentally or record contradictory identity claims. |
| Complaint acceptance | The Admin form preselected the submitter's provisional group, so acceptance could appear to confirm a route without an explicit group choice. The service did not receive the confirmation flag. | The routing selector starts blank. The Admin must choose a group and confirm it; the route passes that confirmation to the service, which rejects acceptance without it. | Admin review now makes the routing decision explicit before a complaint enters the accepted workflow. |
| Frontend/backend rule alignment | Several browser forms allowed inputs that the server would reject, including too many teaching assignments, short synthetic-fixture evidence, oversized roster input, and whitespace-only complaint text. | Matching client checks now cover those cases, attendance membership and correction reason lengths, and event date/publish requirements. The same limits remain enforced on the server. | Fewer avoidable failed submissions and clearer guidance at the form where the user can fix the issue. |
| Query numbers and parameters | `z.coerce.number()` accepted JavaScript-coercible forms such as exponent notation or decimals before integer checks. Pagination allowed page numbers up to 100,000. Some endpoints ignored unexpected query parameters. | Query integers require canonical decimal strings, obey explicit bounds, and pagination is capped at page 10,000. Selected endpoints whose contract takes no query parameters now reject extras; image cache-version parameters are validated when supplied. | Requests have predictable parsing, duplicate or malformed parameters fail clearly, and extreme offsets are bounded. |
| Image uploads | The browser URI-encoded the filename, while server extension checks compared it as plain text. Raw parsers accepted every content type and relied on later checks. | A shared decoder processes the filename once, rejects malformed encoding, path separators, control characters, and names over 255 characters, then checks its extension against the decoded image format. Upload routes check JPEG/PNG MIME type before parsing and restrict the raw parser to those types. Existing byte decoding and size limits remain in force. | Valid filenames work consistently for complaint attachments and event posters, while malformed names and unsupported upload types fail at the request boundary. |
| Validation errors | Routes had duplicated parsers, concatenated unstructured messages, or returned endpoint-specific generic messages. The frontend displayed only a top-level error. | Shared `parseInput` produces a consistent `VALIDATION_ERROR` response with a bounded list of `{field, message}` details. Invalid JSON and oversized bodies have `INVALID_JSON` and `PAYLOAD_TOO_LARGE` codes. The API client shows field details, including for direct image uploads. | Users and maintainers can identify the field that needs correction without exposing request contents or database errors. |

## Scope and safeguards

- Unknown fields continue to be rejected by strict object schemas. Identity, role, ownership, workflow state, and database relationships are still checked in backend services; frontend controls do not grant authority.
- Image byte validation still checks actual decoded content, dimensions, animation, size, and MIME/format agreement. Filename validation supplements these checks; it does not replace them.
- Environment configuration parsing still uses coercion for numeric environment variables. Those values are not request inputs.
- Request schema validation is different from business-state validation. For example, whether a Supervisor is currently eligible or whether an attendance correction matches the current roster must be checked against the database at operation time.
